# Bench 操作手册

## 这是什么

`bench_runner.py` 是 REBUILD 的对照实验脚手架。它解决的问题是：**让「REBUILD 到底比普通提示词好多少」这个问题，用数据回答，而不是靠宣传。**

仅用 Python 标准库，无第三方依赖。

## 五步流程

```bash
# 1. 生成盲评清单（每个用例 × 3 组 × N 次）
python bench/bench_runner.py generate --runs 3

# 2. 拿到空白评分表
python bench/bench_runner.py template

# 3. 合并评审结果（至少两位评审，各自评完全部条目）
python bench/bench_runner.py import runs/review_1.csv runs/review_2.csv

# 4. 揭示身份并写入 scorecard
python bench/bench_runner.py reveal

# 5. 汇总并检查门槛
python bench/bench_runner.py summarise
```

## 三组配置

| 组 | 内容 | 目的 |
|---|---|---|
| A | `bench/prompts/A_plain.txt` — 普通「资深营销顾问」提示词 | 基线 |
| B | `bench/prompts/B_skill.txt` — 结构化目标导向框架 | 有结构但无 REBUILD 纪律 |
| C | `harness/deepseek/SKILL.md` — REBUILD 全流程 | 实验组 |

**注意**：B 组使用的是通用的目标导向分析框架。如果你希望与某个具体竞品（如 marketingskills 的某项技能）对照，只需把该技能原文放进 `prompts/B_skill.txt` 并在 CHANGELOG 说明。这比自建弱基线更有说服力。

## 盲评如何保证有效

脚本用 SHA-256 从 `用例 + 配置 + 运行序号 + 盐值` 生成编号，并把呈现顺序打乱。评审看到的是 `X-XXXXXXXXXX`，无从判断配置身份。

关键防护（已实测验证）：

| 防护 | 行为 |
|---|---|
| 编号重复检测 | 同配置多次运行获得不同编号，评审无法从重复推断 |
| 同 salt 可复现 | 相同 `--salt` 产生完全相同的顺序，便于复核 |
| 单一评审拒绝 | 少于 2 名独立评审时 `reveal` 报错 |
| 覆盖完整性 | 任一评审未评完全部条目即拒绝，避免样本量不等 |
| 评审一致性检查 | 两人分差 > 6 分时提示复核，不自动取平均 |

## 评审要求

至少 **2 名独立评审**，每人评完全部条目。评审规程见 `REVIEW_PROTOCOL.md`。

其中最重要的一条：**A 组（基线）不应由 REBUILD 作者单独评分**。你是方法论的作者，对自己的方案有系统性高估倾向。若只能找到一位评审，至少应是不了解 REBUILD 方法论的人。

## 门槛

预设目标（`RUBRIC.md` 中的初始假设，非既有成绩）：

- C 组均分 ≥ 24/32
- C 组诚实性无 0 分样本
- C 组相对 A 组提升 ≥ 15%
- 关键数字可复算率 ≥ 90%

**未达标也是有效结果。** 如实记录并分析原因，不要调整量表或丢弃失败样本。这是本项目最看重的一点。

## 结果发布

`scorecard.csv` 记录逐条评分，`runs/reveal_key.json` 记录对照关系。发布结果时：

1. 公布 `scorecard.csv` 全文，不只给平均分
2. 公布失败样本原文
3. 写明模型版本、提示词版本、运行日期
4. 若未达门槛，写明未达与原因

`runs/` 目录含未公开的回答内容与盐值，默认不提交（见 `.gitignore`）。如需公开完整可复现记录，删除该行并单独说明。

## 常见问题

**Q：N 次运行要几次？**
规程要求每组至少 3 次，用于观察方差。首次验证可用 `--runs 1` 快速走通流程，但结论强度不足以发布。

**Q：一定要用两个模型吗？**
不必。但若使用同一模型跑三组，结论只能说明「方法论差异」，不能说明「换模型更有用」。

**Q：评审找不到人？**
找不熟悉本方法论的同行最理想。退一步：找两位与营销无关但具备逻辑评估能力的人，至少能保证不是 REBUILD 的既得利益方。
